## 2. 푸시 알림 인프라 구축 (커밋 `fb2d6bb`)

### 진단: 무엇이 막혀 있었나

`/me` 푸시 토글에서 "테스트 알림 보내기" 클릭 → 다음 오류 동시 관찰:

```
GET .../rest/v1/notifications?... 404 (Not Found)
POST .../functions/v1/push-send 가 CORS 차단 (preflight)
```

직접 진단으로 3가지 문제 확정:

1. **`notifications` 테이블 자체가 신DB에 부재** — `to_regclass = null`. 우리 `migration-add-notifications.sql`이 적용된 적 없음. 인앱 알림 INSERT/SELECT 전부 404.
2. **`push_subscriptions` 스키마 불일치** — 신DB에 이미 100건 운영 중(`men.daesol.kr` 공유 테이블). 실제 스키마:
   - `id uuid`, `account_id text NOT NULL`, `username text NOT NULL`, `endpoint text UNIQUE`, `subscription jsonb`, `is_mobile boolean NOT NULL`, `created_at`
   - 우리 push-subscribe 코드는 `account_id`를 number로, `username`/`is_mobile`은 미전달 → 매번 NOT NULL 위반.
3. **Edge Function 미배포** — `push-subscribe`/`push-send` 모두 HTTP 404.

### 외부 담당자 협업

`docs/deploy-push-functions.md` 절차로 1차 요청. 외부 담당자 회신: 시크릿명을 `MAT_VAPID_PUBLIC_KEY`/`MAT_VAPID_PRIVATE_KEY`로 분리(men 측 VAPID 키 충돌 회피)하고 push-send 배포. push-subscribe는 우리 git 원본 그대로 배포 → 위 #2 문제로 INSERT 실패.

curl POST 검증:
```
{"error":"null value in column \"username\" of relation \"push_subscriptions\" violates not-null constraint"}
HTTP 500
```

### 변경 (6 files)

| 파일 | 변경 |
|------|------|
| `supabase/functions/push-subscribe/index.ts` | `account_id: String(userId)` (text 캐스팅), `username`·`is_mobile` 컬럼 INSERT 추가. `username` 누락 시 `accounts` 에서 보충. |
| `supabase/functions/push-send/index.ts` | 시크릿 우선순위 `MAT_VAPID_*` → `VAPID_*` (fallback). `account_id` 조회 시 `String(userId)` 명시. |

### RLS 강화 SQL — `scripts/migration-tighten-notifications-rls.sql`

운영 적용은 외부 담당자 요청용으로 SQL만 작성. 핵심:

```sql
CREATE FUNCTION public.auth_account_id() RETURNS BIGINT
LANGUAGE SQL STABLE SECURITY DEFINER AS $$
  SELECT NULLIF(SPLIT_PART(COALESCE(auth.jwt()->>'email', ''), '@', 1), '')::BIGINT;
$$;
```

JWT email 의 `<id>@daesol.el` 접두를 BIGINT 로 추출. 정책:

- `notifications`: SELECT/UPDATE/DELETE 는 `user_id = auth_account_id()` 본인 행만. INSERT 는 `authenticated` 전체 허용 (타인에게 알림 보낼 수 있어야 함)
- `push_subscriptions`: 본인 행만 (`account_id = auth_account_id()::TEXT`). men 측과 공유 테이블이므로 동일 email 규약(`<id>@daesol.el`) 전제

`service_role` 은 RLS 우회되므로 Edge Function(`push-send`/`push-subscribe`) 영향 없음.
