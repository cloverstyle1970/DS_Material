## 1. 발주서 묶음 편집 — 미완 부분 보완

이전 세션에서 만든 골격(`scripts/migration-add-po-batch-id.sql` + `/purchase-orders/edit?id=N` 라우트 + `PurchaseOrderEntry`에 `editId` prop 추가, `RequestsClient`의 모달 제거)을 받아 빈틈 두 개를 메움.

### 1-1. 편집 모드에서 신규 행 추가가 불가능
- 로딩 후 행이 기존 PO뿐이라 자재신청 참조 외에는 새 품목을 더할 수단이 없음.
- 수정: `siblings` 로 로드한 행 뒤에 `newRow()` 한 개를 항상 부착.

### 1-2. `confirm()`을 `setRows` 콜백 안에서 호출
- React StrictMode에서 reducer 두 번 실행 → 확인창이 두 번 떠 보일 수 있음.
- 수정: `confirm` 을 콜백 밖으로 추출. 외부에서 사용자 응답 확인 후 `setRemovedExistingIds` + `setRows` 호출.

### 1-3. 잔재 정리
- `prev.length <= 1 ? (isEdit ? [newRow()] : [newRow()])` 동일 분기 → 단순화.

### 1-4. AdminShell 라우팅 확인
- `/purchase-orders/edit` 는 `PAGE_REGISTRY` 미등록이라 `AdminShell`이 `children`(page.tsx)로 자동 렌더 → 별도 등록 불필요.
- 권한은 `matchMenuHref` longest-prefix 매칭으로 `/purchase-orders` 권한이 그대로 적용됨.

## 3. material_units 자동 동기화 요구

사용자 추가 요구: S/N 변경 시 `material_units` 상태도 같이 맞춰야 함.

### 3-1. JS 오케스트레이션(1차 구현)
mock-router 안에 분기 로직:
- 변경 없음 → 현장만 바뀐 경우라도 추적 unit의 `current_site` 갱신
- 입고 → 텍스트만 갱신
- 출고 + `return_status='returned'` → **거부**
- 출고 + 비추적 자재 → 텍스트만 갱신
- 출고 + 추적 자재 + 빈 S/N → **거부** (추적 자재는 S/N 필수)
- 출고 + 추적 자재 + 미등록 S/N → **거부**
- 출고 + 추적 자재 + 사용중 S/N → **거부**
- 정상 케이스 → 새 unit `출고`/`반납대기`, 기존 unit `재고` 복원, `transactions.material_unit_id` 갱신

### 3-2. RPC로 원자화 (2차)
JS 다중 UPDATE는 동시성 위험·중간 실패 가능성 → `edit_transaction_serial(p_transaction_id, p_new_serial)` RPC로 옮김.
- `scripts/migration-edit-transaction-serial.sql` 신규.
- plpgsql, `FOR UPDATE` 잠금으로 transactions/material_units 행 락 → 원자적 스왑.
- 입력 정규화: trim + 빈 문자열 → NULL.
- 반환 `{ record }` / `{ error: "..." }` 패턴 (기존 `mark_return_completed`와 동일).

### 3-3. mock-router 정리
- 추적 자재 분기를 `supabase.rpc("edit_transaction_serial", ...)` 단일 호출로 교체.
- RPC 미배포(마이그레이션 미실행) 케이스를 메시지로 안내: `"S/N 자동 동기화 RPC가 배포되지 않았습니다. scripts/migration-edit-transaction-serial.sql 실행 필요."`
- 비추적·입고·`site only 변경` 경로는 기존 JS 경로 유지.

### 3-4. 사용자 마이그레이션 실행 완료 보고
- 검증 시나리오 7가지 안내 (정상 케이스 / 이미 사용중 / 미등록 / 빈 S/N / 반납완료 / 비추적 자재 / 현장만 변경).

## 5. 과거 날짜 발주 입력 400 오류

### 5-1. 증상
- 사용자 보고: "오늘 이전의 날짜로 발주서 입력 → 400".

### 5-2. 분석
- 실제 원인은 날짜 아님. 모든 신규 발주가 `batch_id` 컬럼을 INSERT 페이로드에 포함 → 컬럼 없으면 Supabase 400.
- 사용자에게 `scripts/migration-add-po-batch-id.sql` 실행 여부 질의 → "아직 실행 안 함" 응답.
- 안내: 해당 SQL을 Supabase Dashboard → SQL Editor에서 1회 실행하면 해결. "과거 날짜"는 우연한 트리거였고 오늘 날짜 신규 발주도 동일 실패였을 것.
