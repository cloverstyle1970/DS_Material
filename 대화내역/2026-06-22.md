## 1. 견적서 저장 후 목록 자동 새로고침 (커밋 `83ceb8f`)

### 진단

사용자 보고: "발주/입고/출고는 저장 후 리스트 탭 클릭 시 새로고침되는데, 견적서 작성 후 목록 탭은 stale 데이터가 보인다."

기존 패턴(발주/입고) 비교:

| 위치 | 메커니즘 |
|---|---|
| `PurchaseOrderEntry.tsx:351` | `window.dispatchEvent(new CustomEvent("ds:purchase_orders_changed"))` |
| `InboundEntry.tsx:289` | `window.dispatchEvent(new CustomEvent("ds:transactions_changed", { detail: { mode: "입고" } }))` |
| `RequestsClient.tsx:243` | `useReloadOnActivate(reloadData)` — 숨김→활성 전환 시 reload |
| `RequestsClient.tsx:252-253` | `window.addEventListener("ds:purchase_orders_changed", refreshOrders)` — 백그라운드에서도 즉시 반영 |

`useReloadOnActivate`는 `TabActivationContext.tsx:27`의 훅으로, AdminShell이 탭별로 주입한 `isActive`가 false→true 순간에만 reload 호출(최초 mount는 컴포넌트 자체 fetch가 이미 처리하므로 중복 방지).

견적서는 둘 다 없음:
- `QuoteEntryClient.save()` — 저장 성공 후 이벤트 dispatch 없음 (신규: 폼 리셋만, 수정: `router.push`)
- `QuotesListClient` — `useEffect(() => { load(); }, [])` 1회만, 리스너·재활성화 훅 모두 없음

### 적용

`QuoteEntryClient.tsx` — 수정/신규 양쪽 성공 직후 `window.dispatchEvent(new CustomEvent("ds:quotes_changed"))` 추가 (각각 line 862, 925).

`QuotesListClient.tsx`:

```tsx
import { useCallback, useEffect, useState } from "react";
import { useReloadOnActivate } from "@/context/TabActivationContext";

const load = useCallback(async () => { /* ... */ }, []);
useEffect(() => { load(); }, [load]);
useReloadOnActivate(load);
useEffect(() => {
  const onChanged = () => { load(); };
  window.addEventListener("ds:quotes_changed", onChanged);
  return () => window.removeEventListener("ds:quotes_changed", onChanged);
}, [load]);
```

기존 `async function load()` 선언을 `useCallback`으로 감싸 의존성 안정화. `deleteQuote`/`changeStatus`에서 호출하는 `load()`도 그대로 동작(컴포넌트 스코프 내).

## 2. 견적·자재청구 등록 시 박은숙·황진한 고정 알림 (커밋 `5bd931d`)

### 진단

사용자 요청: "견적 및 자재청구 등록되면 사용자 박은숙·황진한에게 알림 발송하도록 검토해줘."

`/claim/new`(`ClaimEntryClient`) 페이지 헤더가 "🔧 견적 및 자재청구 등록" — 3가지 모드 분기:

- **유상견적요청** → `quote_requests` insert. 이미 알림 있음 — `admin` 또는 `menu:/claim/quote-requests:read` 권한 보유자 전원, 신청자 본인 제외.
- **무상신청 / 당직선출고** → `material_requests` insert. **알림 없음**.

박은숙·황진한은 코드 곳곳에 자재관리 담당으로 이미 하드코딩(`InboundEntry.tsx:69`, `MaterialRequestEntry.tsx:45`, `OutboundEntry.tsx:151`, `PurchaseOrderEntry.tsx:98`, `PurchaseOrderModal.tsx:34-35` — DS=황진한, TK=박은숙). 이름 기반 `accounts` 조회가 기존 패턴과 일관.

### 사용자 결정

3가지 질문으로 정리:

1. **적용 범위**: 3가지 모드 모두
2. **유상견적요청 기존 권한 기반 알림**: 제거하고 박은숙·황진한만
3. **본인 제외 여부**: 본인 포함 (신청자가 박은숙/황진한이어도 알림 받음)

### 적용

`ClaimEntryClient.submit()` 전체 재구성:

```ts
// 호기 헤더 — 견적요청/자재청구 알림 메시지 공용 (기존엔 유상 분기 내부에만 있었음)
const elevSet = Array.from(new Set(validItems.map(r => r.elevator_name.trim()).filter(Boolean)));
const headerElev = elevSet.length === 0 ? null : elevSet.join(", ");
const firstName = validItems[0]?.material_name ?? "";
const summary = validItems.length <= 1 ? firstName : `${firstName} 외 ${validItems.length - 1}건`;

const NOTIFY_RECIPIENTS = ["박은숙", "황진한"] as const;
async function notifyRecipients(payload: {
  type: string; title: string; message: string; link: string; refType: string; refId: number | null;
}) {
  const { data: targets } = await supabase.from("accounts")
    .select("id").in("name", NOTIFY_RECIPIENTS as unknown as string[]);
  const targetIds = (targets ?? []).map(a => a.id as number);
  await Promise.all(targetIds.map(uid => insertNotification({ userId: uid, ...payload })));
}
```

- 유상견적요청: 기존 권한 기반 fan-out 25줄 삭제 → `notifyRecipients(...)` 호출 한 줄로 교체.
- 무상신청/당직선출고: `material_requests` insert에 `.select("id").single()` 붙여 `refId`로 사용. 알림 타이틀은 모드별 분기("새 당직선출고 신청…" / "새 무상자재신청…"), 링크는 `/requests`.
- 실패 처리: 기존과 동일 silent — `.catch(e => console.warn(...))`로 등록 흐름 차단 X.

### 메모리 정책 메모

작업 도중 사용자가 DB 비밀번호를 평문 전달했지만 이번 작업은 코드만 손대므로 메모리에 저장하지 않음. 신DB 좌표 메모리 [[reference_newdb_connection]]는 "비밀번호 제외" 정책 유지.

## 3. 개발서버 재시작 — TaskStop의 한계

### 진단

`TaskStop`으로 dev 서버를 종료했는데 새 `npm run dev` 시작이 실패:

```
⚠ Port 3000 is in use by process 2108, using available port 3001 instead.
⨯ Another next dev server is already running.
- PID: 2108
- Dir: H:\DS_Material
Run taskkill /PID 2108 /F to stop it.
```

`TaskStop`은 npm wrapper(.cmd) 프로세스만 종료하고 그 자식 Node(Next dev)는 남는다. Next dev 자체가 두 번째 인스턴스를 감지해 거부.

### 조치

`Stop-Process -Id 2108 -Force` (PowerShell)로 명시 종료 후 재기동. 첫 시도는 Git Bash의 path mangling으로 `taskkill /PID` 가 `'C:/Program Files/Git/PID'`로 깨져 실패 — PowerShell로 우회.

향후 dev 서버 재시작 시 같은 함정 가능성. 권장 패턴:

```powershell
Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -like "*next dev*" } | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

또는 Bash 통일이 필요하면 인수만 따옴표:

```bash
taskkill "/PID" 2108 "/F"
```
