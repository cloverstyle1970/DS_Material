## 1. 문제 재현·근본 원인 조사

사용자 문의: "발주 2개 중 1개만 입고하면 나머지 1개가 미입고로 남아야 하는데 발주관리에서 모두 입고완료로 표시된다"

Explore 서브에이전트로 발주/입고 전 흐름 전수 조사 결과 **부분입고 미지원 3중 결함** 확인:

|---|---|---|
| ① 스키마 | `mock-router.ts:461-487` (dbToOrder) | `purchase_orders` 에 `received_qty` 컬럼 없음, `status` enum 도 발주/입고완료/취소 3가지뿐 |
| ② 저장 로직 | `InboundEntry.tsx:293-303` | 입고량과 발주량 비교 없이 `orderIds` 전량에 `status='입고완료'` UPDATE |
| ③ 조회 필터 | `InboundEntry.tsx:876-895` (OrderPopup) | `status='발주'` 필터 + `transactions.note '발주 #N'` 언급된 발주 제외 → 부분입고 잔량 조회 불가능 |

### 실질적 batch_id 흉내

발주 로직을 자세히 보니 `PurchaseOrderEntry` 는 1 발주서 저장 시 **여러 `purchase_orders` 행을 저장**하고 `batch_id` 로 헤더 정보(vendor·ship_*·order_no 등)를 중복 저장하며 편집 시 sibling 을 다시 로드하는 방식. 이미 "헤더/라인 분리를 flat 테이블로 흉내낸 상태" 였음.

## 3. 마이그레이션 SQL

**신규 파일**: `scripts/migration-purchase-orders-header-lines.sql`

### 3-1. 신 스키마

```sql
CREATE TABLE purchase_orders (
  id             BIGINT PRIMARY KEY,       -- SERIAL 아님: legacy 대표 id 재사용
  order_no       TEXT,
  status         TEXT NOT NULL DEFAULT '발주',  -- 발주 | 부분입고 | 입고완료 | 취소
  vendor_name    TEXT,
  site_name      TEXT,
  requester_name TEXT,
  ordered_at     TIMESTAMPTZ NOT NULL,
  received_at    TIMESTAMPTZ,
  order_ref_no   TEXT,                     -- 신설: 외부 참조번호(MNG…) 별도 컬럼
  form_type      TEXT NOT NULL DEFAULT '기본',  -- 기본 | 긴급 | 수리 (신설)
  note           TEXT,
  user_id        BIGINT NOT NULL,
  user_name      TEXT NOT NULL,
  ship_to, ship_due_date, ship_receiver, ship_contact, ship_manager, ship_note  TEXT,
  created_at, updated_at TIMESTAMPTZ
);

CREATE TABLE purchase_order_lines (
  id            BIGSERIAL PRIMARY KEY,
  order_id      BIGINT NOT NULL REFERENCES purchase_orders(id) ON DELETE CASCADE,
  line_no       INTEGER NOT NULL DEFAULT 1,
  material_id   TEXT NOT NULL,
  material_name TEXT NOT NULL,
  qty           INTEGER NOT NULL CHECK (qty > 0),
  received_qty  INTEGER NOT NULL DEFAULT 0 CHECK (received_qty >= 0),
  unit_price    NUMERIC,
  elevator_name TEXT,
  request_id    BIGINT,                    -- 자재신청 참조
  note          TEXT,
  status        TEXT NOT NULL DEFAULT '발주',
  created_at, updated_at TIMESTAMPTZ
);
```

### 3-2. 핵심 트릭

1. **헤더 id = 그룹 대표 legacy id 재사용**  
   `batch_id` 그룹의 `MIN(id)` 를 신 헤더 id 로 유지 → `notifications.ref_id` (헤더 대표 id 참조) 가 대부분 자동으로 유효. `SEQUENCE OWNED BY` 로 채번용 시퀀스 분리.

2. **note 태그 분리**  
   `[orderRefNo][긴급|수리] remark` 형식이던 note 를 정규식으로 파싱해 `order_ref_no`, `form_type`, `note` (remark) 컬럼으로 분리.

3. **transactions.note sentinel rewrite** (핵심 안전장치)  
   naive rewrite 시 "새 id 값이 다른 legacy id 와 겹쳐 재매칭" 되는 위험. 두 단계 처리:
   - 1단계: `발주 #<legacy_id>` → `발주 §<new_line_id>§` (sentinel 로 격리)
   - 2단계: `발주 §N§` → `발주 #N` (최종 복원)

4. **매핑 테이블 유지** (`purchase_orders_migration_map`)  
   `legacy_id → new_order_id, new_line_id` 매핑을 물리 테이블로 보존해 사후 검증·재적용 가능.

### 4-2. API 재작성 (`src/lib/mock-router.ts`)

| 엔드포인트 | 동작 |
|---|---|
| `GET /api/purchase-orders?status=발주,부분입고` | 콤마 리스트 필터 지원. 헤더+라인 join 해서 라인 단위 flat 배열 반환 |
| `GET /api/purchase-orders/:orderId` | 특정 발주서(헤더+라인) 조회 |
| `POST /api/purchase-orders` | body `{ header, lines[] }` 통합 저장 |
| `PATCH /api/purchase-orders/:orderId` | action: `저장`(헤더수정+라인 upsert+삭제) / `입고완료`(전 라인 잔량 입고) / `취소` / `헤더수정` |
| `PATCH /api/purchase-orders/lines/:lineId` | action: `입고완료` / `취소` (라인 단위) |
| `DELETE /api/purchase-orders/lines/:lineId` | 라인 삭제 + 마지막 라인이면 헤더도 CASCADE |
| `DELETE /api/purchase-orders/:orderId` | 헤더 삭제 (CASCADE 로 라인도) |

### 4-3. 자동화 훅 (핵심)

**`POST /api/transactions`** — 입고 트랜잭션 저장 시 note 에 `발주 #<line_id>` 패턴이 있으면 자동으로:
1. 라인 `received_qty += qty` (qty 초과 방지)
2. 라인 status 재계산 (received_qty vs qty)
3. 헤더 status 재계산 (`refreshHeaderStatus()`)
4. 헤더 received_at 갱신

**`DELETE /api/transactions/:id`** — 트랜잭션 삭제 시 대칭 롤백 (received_qty 감산 + 상태 재계산).

→ 클라이언트는 note 규약만 지키면 되고, 발주 상태 관리는 완전히 서버측 자동 처리.
