### 5-3. 디버깅 4단계 — 백엔드 검증
초기 호출 시 클라이언트 "Failed to fetch". 백엔드 직접 curl로 좁힘.

| 단계 | 증상 | 원인 | 조치 |
|---|---|---|---|
| 1 | OPTIONS 500 (WORKER_ERROR) | `setVapidDetails` 모듈 init 단계에서 실패 (실제로는 subject 형식 에러였음) | `setVapidDetails`를 `serve` 안으로 이동 |
| 2 | 401 UNAUTHORIZED_INVALID_JWT_FORMAT | anon key가 신형식 `sb_publishable_*`라 Edge Function의 JWT verification 통과 불가 | 두 Function `--no-verify-jwt`로 재배포 (본 프로젝트 RLS `allow_all` 모델과 일관) |
| 3 | "Vapid subject is not a valid URL" | 사용자가 Dashboard에 `mailto:` 접두사 없이 이메일만 등록 | Function 내부에서 `mailto:` 자동 보정 |
| 4 | "Vapid public key must be a URL safe Base 64 (without \"=\")" — 디버그 출력으로 키 길이 90자 확인 (정상 87) | Dashboard 등록 값에 비-base64 문자(공백/줄바꿈) 3자 끼임 | `trim()` + `[^A-Za-z0-9_-]` 제거 정규식 추가 |

최종: `curl POST` → `{"sent":0,"reason":"no_subscription"}` (정상 흐름, 등록 구독 없음).

### 5-4. 클라이언트 디버깅
사용자 시나리오에서 [테스트 알림] → `sent:0 / no_subscription`. user.id=15에 구독 row가 없는 상태.

원인: 이전 시도 시 push-subscribe가 401로 실패 → 브라우저 `pushManager` 상태는 살아있는데 DB는 비어있는 stale 상태. [해제]→[구독] 다시 해도 동일.

진단 강화: push-subscribe 응답에 `upserted` row + `total_for_user` count 임시 노출 + 클라이언트에서 `alert(JSON.stringify(result))`. 사용자가 한 번 더 시도하니 즉시 정상 응답·DB 입력 → 푸시 도착. **앞 단계 trial이 미스 직전 상태를 만들었던 것**.

디버그 코드 모두 원복 후 클린 재배포.
