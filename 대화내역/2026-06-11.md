## 1. met.daesol.kr 외부서버 `crypto.randomUUID` 오류

### 증상
외부서버 `http://met.daesol.kr/purchase-orders/new` 등에서 "전표 입력" 클릭 시 `This page couldn't load`. 콘솔 에러:

```
Uncaught TypeError: crypto.randomUUID is not a function
```

개발서버(`localhost:3000`)는 정상.

### 원인
- `crypto.randomUUID()`는 **Secure Context(HTTPS 또는 localhost)에서만** 동작
- `met.daesol.kr`이 HTTP로 서빙되고 있어 브라우저가 API를 비활성화
- 코드 21곳에서 `crypto.randomUUID()` 호출 (InboundEntry, OutboundEntry, PurchaseOrderEntry, MaterialRequestEntry, QuoteEntryClient, UniformSafety* 등)

### 해결
**옵션 A 선택(권장)**: GitHub Pages "Enforce HTTPS" 활성화로 SSL 자동 발급
- 코드 수정 없이 인프라 수준에서 해결
- 다른 Secure Context API(Service Worker, 클립보드, PWA 등)도 함께 활성화

### 적용 과정
1. 배포 환경 확인: GitHub Pages 정적 export (`output: "export"`)
   - `public/CNAME = met.daesol.kr`
   - 워크플로우: `.github/workflows/deploy.yml`
   - 저장소: `github.com/cloverstyle1970/DS_Material`
2. 사용자에게 안내한 절차:
   - GitHub repo → Settings → Pages → "Custom domain" 등록 확인
   - "Enforce HTTPS" 체크박스 활성화 (Let's Encrypt 자동 발급)
3. **사용자 적용 완료** — `https://met.daesol.kr/me` 정상 표시 확인

### 미해결
- 인증서 발급 직후 입고/발주 페이지에서 실제로 `crypto.randomUUID` 오류가 사라졌는지 최종 확인 못함 (다른 이슈로 흐름 전환)

## 3. 입고전표 저장 시 발주 status 미갱신

### 증상
입고전표(`/inbound/new`)에서 "발주서 참조" 팝업을 열면 이미 입고완료 처리한 발주도 미입고 리스트에 표시됨.

### 원인 분석
- `OrderPopup`은 `api.get("/api/purchase-orders?status=발주")`로 발주 status="발주"인 row만 조회 (정상)
- **두 가지 입고 처리 경로 중 한쪽이 status 갱신을 누락**:
  1. `PATCH /api/purchase-orders/:id { action: "입고완료" }` — mock-router `routePATCH` 1367-1369에서 `status="입고완료"`로 갱신 ✅
  2. **입고전표(`InboundEntry.save()`)** — `api.post("/api/transactions", ...)`만 호출하고 `purchase_orders.status` 갱신 안 함 ❌
- `applyMultipleOrders`(line 166-189)에서 `rows[i].orderId = o.id`로 발주 ID를 보관하긴 하지만 save() 끝부분에서 사용하지 않음

### 수정 (`src/components/purchase/InboundEntry.tsx`)
import에 `supabase` 추가 후, save()에서 transaction 생성 직후 `orderId` 모아서 일괄 PATCH:

```ts
const orderIds = Array.from(new Set(
  valid.map(r => r.orderId).filter((id): id is number => id !== null)
));
if (orderIds.length > 0) {
  const receivedAtIso = new Date(`${inboundDate}T00:00:00Z`).toISOString();
  await supabase.from("purchase_orders")
    .update({ status: "입고완료", received_at: receivedAtIso })
    .in("id", orderIds);
}
```

### 부수 발견 / 미정리 데이터

### B. 입고전표 발주 status 미갱신 — 기존 데이터 정리

이번 커밋(`21d922a`)으로 신규 입고는 정상 처리되지만, **과거에 입고전표로 처리됐지만 발주 status가 "발주"로 남아있는 데이터**는 OrderPopup 미입고 리스트에 계속 노출됨.

#### 정리 후보 SQL (확인 후 적용)
```sql
-- 후보 조회: 입고 transaction이 있는데 발주는 "발주" status인 row
SELECT po.id, po.material_name, po.qty, po.status, po.ordered_at,
       t.id AS tx_id, t.note, t.created_at AS inbound_at
FROM purchase_orders po
JOIN transactions t ON t.type = '입고'
  AND (t.note LIKE '%발주#' || po.id || '%' OR t.note LIKE '%발주 #' || po.id || '%')
WHERE po.status = '발주'
ORDER BY po.ordered_at DESC;

-- 위 결과 검증 후 갱신
UPDATE purchase_orders
SET status = '입고완료',
    received_at = (
      SELECT MIN(t.created_at)
      FROM transactions t
      WHERE t.type = '입고'
        AND (t.note LIKE '%발주#' || purchase_orders.id || '%'
             OR t.note LIKE '%발주 #' || purchase_orders.id || '%')
    )
WHERE id IN ( ... 위 조회 결과 ID 목록 ... );
```

note 패턴 매칭은 보수적으로 — 잘못 매칭된 발주는 사용자 검수 필요.
