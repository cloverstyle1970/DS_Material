## 1. met.daesol.kr 외부서버 `crypto.randomUUID` 오류

### 증상
외부서버 `http://met.daesol.kr/purchase-orders/new` 등에서 "전표 입력" 클릭 시 `This page couldn't load`. 콘솔 에러:

```
Uncaught TypeError: crypto.randomUUID is not a function
```

개발서버(`localhost:3000`)는 정상.

### 원인
- `crypto.randomUUID()`는 **Secure Context(HTTPS 또는 localhost)에서만** 동작
- `met.daesol.kr`이 HTTP로 서빙되고 있어 브라우저가 API를 비활성화
- 코드 21곳에서 `crypto.randomUUID()` 호출 (InboundEntry, OutboundEntry, PurchaseOrderEntry, MaterialRequestEntry, QuoteEntryClient, UniformSafety* 등)

### 해결
**옵션 A 선택(권장)**: GitHub Pages "Enforce HTTPS" 활성화로 SSL 자동 발급
- 코드 수정 없이 인프라 수준에서 해결
- 다른 Secure Context API(Service Worker, 클립보드, PWA 등)도 함께 활성화

### 적용 과정
1. 배포 환경 확인: GitHub Pages 정적 export (`output: "export"`)
   - `public/CNAME = met.daesol.kr`
   - 워크플로우: `.github/workflows/deploy.yml`
   - 저장소: `github.com/cloverstyle1970/DS_Material`
2. 사용자에게 안내한 절차:
   - GitHub repo → Settings → Pages → "Custom domain" 등록 확인
   - "Enforce HTTPS" 체크박스 활성화 (Let's Encrypt 자동 발급)
3. **사용자 적용 완료** — `https://met.daesol.kr/me` 정상 표시 확인

### 미해결
- 인증서 발급 직후 입고/발주 페이지에서 실제로 `crypto.randomUUID` 오류가 사라졌는지 최종 확인 못함 (다른 이슈로 흐름 전환)

```sql
-- 후보 조회: 입고 transaction이 있는데 발주는 "발주" status인 row
SELECT po.id, po.material_name, po.qty, po.status, po.ordered_at,
       t.id AS tx_id, t.note, t.created_at AS inbound_at
FROM purchase_orders po
JOIN transactions t ON t.type = '입고'
  AND (t.note LIKE '%발주#' || po.id || '%' OR t.note LIKE '%발주 #' || po.id || '%')
WHERE po.status = '발주'
ORDER BY po.ordered_at DESC;

-- 위 결과 검증 후 갱신
UPDATE purchase_orders
SET status = '입고완료',
    received_at = (
      SELECT MIN(t.created_at)
      FROM transactions t
      WHERE t.type = '입고'
        AND (t.note LIKE '%발주#' || purchase_orders.id || '%'
             OR t.note LIKE '%발주 #' || purchase_orders.id || '%')
    )
WHERE id IN ( ... 위 조회 결과 ID 목록 ... );
```

### 5. 유지보수 사이트 SSO 연동 — 검토→구현

이전 메모(`project_maintenance_site_sso`)는 Edge Function JWT 발급/검증 방식이었지만, 그 사이 자재관리가 Supabase Auth로 전환되어(2026-06-05) 같은 프로젝트 토큰을 그대로 신뢰할 수 있게 됨. 상대방(유지보수 측) 개발자가 단순화된 URL hash 핸드오프 방식 제안.

**도메인 변경**: 유지보수 `daesol-sketch.github.io` → **`men.daesol.kr`**. 자재관리 `met.daesol.kr`. `met`(Material) ↔ `men`(maintenance) 한 글자 차이.

**합의된 인터페이스**:
```
URL: https://<상대도메인>/#access_token=<JWT>&refresh_token=<JWT>
```

**합의된 정책**:
- 방향: 양방향 (각자 송신부 + 수신부 구현)
- 이동 방식: 같은 창 (`window.location.href`) — 사용자 요청
- 로그아웃 동기화: **하지 않음** — 한쪽 로그아웃해도 다른 쪽 세션 유지
- 권한 없는 사용자: 별도 안내 없음. `accounts.permissions` + AdminShell 가드 그대로

**우리 측 구현** (커밋 `1561db6`, `e41903d`):
- 송신부 `src/components/layout/Sidebar.tsx`:
  - "유지보수" 버튼 `<a>` → `<button>` 변경
  - `openMaintenanceSite()` — 세션 토큰을 hash로 담아 `window.location.href` 같은 창 이동
- 수신부 `src/context/AuthContext.tsx`:
  - `consumeSsoHashIfPresent()` — 모든 페이지 진입에서 hash 토큰 자동 처리
  - `setSession` 호출 후 `history.replaceState`로 즉시 청소
  - 이후 평소 `syncFromSession()`이 `accounts` 권한 fetch

**진단 과정**: 외부서버에서 유지보수 → 자재관리로 진입 시 로그인 화면이 떴음. 임시 console.log 추가(`f292915`) → 콘솔에 SSO 관련 에러 없음을 사용자가 확인 → 상대방 측 송신부 미구현 상태가 원인으로 판명. 로그 제거(`9c8dfeb`).

### 8. 입고전표 발주서 참조 미입고 리스트 일관성 (A+B+C 일괄)

이미 입고완료된 발주가 OrderPopup 미입고 리스트에 잔존하던 문제. 같은 세션 21d922a 커밋(입고전표 저장 시 발주 status 갱신)으로 신규 데이터는 해결됐지만, 사용자가 "오늘 이후 입고 처리된 건도 속함"을 보고. 한 번에 일관성 확보를 위해 세 가지 작업 일괄 처리 (커밋 `bfa8a3c`).

#### A. OrderPopup 안전장치
`InboundEntry.tsx`의 OrderPopup useEffect 보강. `status='발주'` 뿐 아니라 `transactions` type=입고 + note `발주 #N` 패턴 매칭 발주는 자동 제외. status 갱신 누락 / 옛 데이터 / 다른 경로 등 모든 케이스 커버.

```ts
Promise.all([
  api.get("/api/purchase-orders?status=발주"),
  supabase.from("transactions").select("note").eq("type", "입고").ilike("note", "%발주%"),
]).then(([rawOrders, txRes]) => {
  const matchedIds = new Set<number>();
  const re = /발주\s*#(\d+)/g;
  // ... note에서 ID 추출, matchedIds에 추가
  setOrders(rawOrders.filter(o => !matchedIds.has(o.id)));
});
```

#### B. InboundEntry note 형식 통일
`applyMultipleOrders`의 remark 초기값을 `발주#${o.id}` → 빈 문자열로. save() 단에서 `r.orderId` 있으면 `발주 #${r.orderId} 입고완료` 표준 패턴 자동 prepend. 사용자 메모는 ` / ` 구분자로 append. 이 패턴이 (1) A 안전장치 정규식 매칭, (2) mock-router 입고 transaction 삭제 시 발주 status 원복(line 1789) 양쪽에서 활용됨.

#### C. 기존 잘못된 데이터 정리 SQL
`scripts/migration-fix-orphaned-inbound-orders.sql` 신설. transactions type=입고 + note `발주 #N` 패턴 매칭 + purchase_orders.status='발주'인 row를 `입고완료` + `received_at`(최초 입고 시각)로 일괄 갱신.

**적용 방식**: 사용자가 비밀번호(`Daesol7792!`)를 직접 적용 옵션(1번)으로 동의. `apply-migration.mjs`로 직접 실행.


**적용 결과**: **12건 보정**, 잔존 0건. 추후 작업 목록 B/C 항목 해소.

**부분 입고**: `purchase_orders`가 1행=1품목 구조라 자동 처리됨. 한 발주서의 일부 row만 처리되어도 미처리 row는 그대로 리스트에 남음 (정상 동작).

### 9. 출고전표 입고내역 참조 안전장치

같은 패턴으로 출고전표(`OutboundEntry.tsx`)도 보강 (커밋 `c378851`).

**원인**: `InboundRefPopup`이 모든 type='입고' transaction을 그대로 노출. 이미 다른 출고전표에 참조된 입고가 계속 후보로 표시.

**수정**: 입고전표 A+B 패턴과 동일.
- `applyInbound`: remark 초기값 `입고#${t.id} 참조` → 빈 문자열
- `save()`: `r.inboundRef`가 있으면 `입고 #${r.inboundRef} 출고완료` 표준 패턴 자동 prepend
- `InboundRefPopup`: 출고 transaction의 note에서 `입고\s*#(\d+)` 패턴 매칭해 참조된 입고 ID 자동 제외

**부분 출고 정책**: 한 번 참조된 입고는 다시 후보로 보이지 않음 — 입고:출고 1:1 매칭 정책. 부분 출고가 필요하면 자재 검색으로 직접 입력. 데이터 정리 SQL은 옛 패턴(`입고#N 참조`)도 정규식이 매칭해 불필요.
