## 1. 입·출고 전표수정 규격 미표시 (`8002452`)

**증상:** 출고관리에서 전표입력 시에는 규격이 표시되는데, 출고관리 리스트 → 전표수정으로 들어가면 규격 칸이 비어 있음.

**원인:** `transactions` 테이블에는 **규격(`model_no`)이 저장되지 않는다.** 규격은 자재 마스터(`materials`)에서 가져와 화면에만 표시하는 값이다.

- **전표입력**: `refreshRowStock()` / `applyMultipleMaterials()` 가 자재 선택 시점에 `m.modelNo` 를 행에 채움 → 표시됨
- **전표수정**: `OutboundEntry.tsx:140` 에서 행 복원 시 `spec: ""` 하드코딩 → 빈칸

같은 이유로 구매단가·재고·보관위치도 수정 모드에서 0/빈값이었고, 거래명세서 미리보기의 규격 칸도 비어 있었음.

**수정:** 수정 모드에서 행 복원 후, 등장하는 자재 ID를 모아 `materials` 를 **한 번에 조회**해 채운다.

```ts
// transactions 에는 규격·재고·보관위치·구매단가가 저장되지 않으므로
// 자재 마스터에서 다시 채운다. 단가(unitPrice)는 전표에 저장된 값이 진리원이라 건드리지 않는다.
const matIds = Array.from(new Set(loaded.map(r => r.materialId).filter(Boolean)));
const { data: mats } = await supabase.from("materials")
  .select("id, model_no, buy_price, storage_loc, stock_qty").in("id", matIds);
```

**핵심 판단 — 기존 `refreshRowStock()` 을 재사용하지 않은 이유:** 그 함수는 자재 마스터의 현재 판매단가로 `unitPrice` 를 덮어쓴다. 수정 모드에서 호출하면 저장 당시 단가(무상 출고·수동 조정 포함)가 유실된다. 그래서 표시용 필드만 채우는 별도 조회로 처리.

**입고도 동일 버그** (`InboundEntry.tsx:115`) — 사용자 요청으로 함께 수정. 입고 `Row` 타입에는 `buyPrice`/`stockQty`/`storageLoc` 필드가 없어(화면에 그 컬럼이 없음) `model_no` 만 조회.

## 4. 모바일 라우트 권한 통합 (`19764bd`)

### 4-1. 발견한 버그

`/safety/risk-assessment/mobile` 이 **권한 등록 4곳 중 `PermissionGroupsClient.tsx` 한 곳에서만 누락**돼 있었음. 두 단계로 문제가 터짐:

1. `permissions.ts` 에 등록돼 있으니 `matchMenuHref("/safety/risk-assessment/mobile")` 가 **자기 자신을 정확 매칭**(longest-prefix라 부모로 안 떨어짐) → `AdminShell` 가드가 `menu:/safety/risk-assessment/mobile:read` 를 요구 → **admin 외에는 아무도 진입 불가.** 정작 대상이 기사
2. 권한그룹 트리에 없으니 그룹 UI에서 그 권한을 **줄 방법이 없음.** 사원등록 개별 권한 모달(`PERMISSION_MENUS` 사용)에서는 줄 수 있지만, 그룹 **"↻ 멤버에 적용"이 `accounts.permissions` 를 덮어쓰기** 하므로 개별로 준 권한이 조용히 날아감

추가로 `RiskAssessmentMobileClient.tsx:16` 이 권한 체크 기준을 PC href로 잡고 있어, 라우트 가드(모바일 href)와 화면 내부 체크(PC href)가 **서로 다른 권한**을 보고 있었음.

### 4-2. 선택지와 결정

- (A) 모바일을 독립 메뉴로 유지 → 권한그룹 트리에 항목 추가 + 클라이언트 HREF 교정
- **(B) 모바일을 PC 메뉴 권한에 종속** ← 채택 (운영상 모바일만 따로 열고 닫을 일이 없음)

### 4-3. 수정

**`permissions.ts`** — `PERMISSION_MENUS` 에서 모바일 href 제거. `ALL_HREFS` 가 여기서 파생되므로 이것만으로 가드가 부모 권한으로 판정.

**`Sidebar.tsx`** — 메뉴 노출 판정도 같은 기준으로 정렬.

```ts
const canonical = matchMenuHref(item.href) ?? item.href;
return hasMenuPermission(user, canonical, "read");
```

이 한 줄이 필요했던 이유: 사이드바는 `hasMenuPermission(user, item.href, "read")` 로 **href 문자열을 정확히** 대조하고 있었다. `permissions.ts` 만 고치면 가드는 통과하는데 **메뉴가 사이드바에 안 뜨는** 상태가 된다. 등록된 href 는 `matchMenuHref` 가 자기 자신을 반환하므로 기존 메뉴는 무영향이고, 앞으로 추가될 하위 라우트도 자동으로 부모 권한을 따른다.

→ 이 메뉴의 **등록 지점이 4곳 → 3곳**으로 축소(`PermissionGroupsClient` 불필요).

**검증:** `matchMenuHref` 를 실모듈 import 해 부모 폴백·기존 매칭 유지 확인.

**적용 후 주의:** 사원등록 개별 권한 모달에서 `위험성평가 등록(모바일)` 을 직접 체크해 준 사원이 있다면 그 권한 문자열은 이제 무시됨 → 부모 권한(`위험성평가 등록`) 보유 여부만 확인하면 됨.

## 5. 참가자 알림 링크를 수신자 기준으로 (`de7b349`)

**문제:** 링크가 **보내는 화면 기준**이었음. PC에서 등록하면 `/safety/risk-assessment`, 모바일에서 등록하면 `/mobile` → 모바일 기사에게 PC 페이지 링크가 감.

**수정:** `src/components/safety/riskNotify.ts` 신설 — 두 등록 화면이 공유하는 알림 헬퍼.

```ts
// 수신자 화면 모드 일괄 조회. 조회 실패·미설정이면 PC(기본값)로 보낸다.
```

- `accounts.view_mode`(환경설정 화면 모드, `AuthContext` 가 로그인 시 읽는 컬럼) 기준으로 수신자마다 링크 분기
- 수신자 전체를 **쿼리 1회**로 조회 → 인원이 늘어도 호출 증가 없음

PC·모바일 클라이언트 각자의 20줄짜리 중복 알림 블록을 헬퍼 호출로 교체.

※ 이 수정은 4번(권한 통합)이 전제 — 두 경로가 같은 권한을 쓰므로 어느 쪽으로 보내도 막히지 않음.

### 9-2. 등록 방식 — 이원화 유지

기존 매뉴얼과 동일하게 두 곳에 넣는다.

- `scripts/migration-add-manual-*.sql` — `manuals` INSERT. **동일 제목 사전 `DELETE` 로 idempotent**, 파일 끝 검증 `SELECT`
- `ManualCenterClient.tsx` 의 `STATIC_FALLBACK_MANUALS` — DB 조회 실패 시에도 노출되도록 같은 본문 유지

파일 5개(유해요인 4종은 한 파일로 묶음). 적용은 메모리의 pooler 직접 접속 패턴으로 처리하고 **일회성 `_apply-*.mjs` 는 매번 실행 직후 삭제**(비밀번호는 `PGPASSWORD` 환경변수로만 전달, 파일·커밋에 미포함).

### 9-3. 렌더러 제약 — 마크다운 표 금지

`MarkdownRenderer` 는 헤더·리스트·인용구·코드블록·이미지·인라인(bold/code/link)만 처리한다. **표 문법(`| |`)은 파싱하지 않아 문단으로 그대로 노출**되므로 모든 표를 목록 또는 코드블록으로 작성했다. (이 대화내역 md 는 GitHub 렌더링이라 표 사용 무관)

### 9-4. 문서화 중 코드로 확인해 매뉴얼에 명시한 사실

매뉴얼 신뢰성의 핵심이라 실제 코드·DB를 확인한 뒤 적었다.

- **TBM 마스터 삭제 동작이 항목별로 다르다** — `pg_constraint` 직접 조회로 확인
  - 안전수칙·체크리스트: `ON DELETE RESTRICT` → **사용 이력이 있으면 삭제 거부**(FK 오류 팝업)
  - 공사구분·고장증상: `ON DELETE SET NULL` → **삭제되며 과거 기록의 값이 비워짐**
  - → 매뉴얼 원칙을 "삭제 대신 비활성"으로 안내
- **마스터 문구 수정은 과거 기록에 소급되지 않는다** — 작성 시 `rule_text`·`item_label`·`hazard` 를 기록에 복사해 보관하는 구조
- **검색어가 서버 조회가 아닌 로드된 목록 안에서만 걸러지는 화면들** — TBM 관리(30건/페이지), 유해요인조사대장·위험성평가대장(각 500건). 기간·구분으로 먼저 좁히도록 주의 문구
- **비통번호 검색은 전화번호 끝 4자리 안에서만 매칭** — `012-2080-3565` 는 `3565` 로 찾히지만 `2080`·전체번호로는 안 찾힘. 또 검색어에 한글·영문이 섞이면 비통 매칭을 건너뜀(`19단` 류의 숫자 오매칭 방지)
- **현장 검색어 입력 시 DS/TK 필터가 무시**되고 전체에서 매칭됨
- **호기 목록의 비상통화장치 빈 칸**은 직전 호기와 같은 번호일 때의 반복 표기 생략이며 미등록(`—`)과 다름
- **자재 수리품 판정** — DS는 코드 끝 `R`, TK는 코드 첫 글자 `A`. 신품과 별개 자재
- **자재 검색 5개 필드**(부품명·코드·별칭·규격·보관장소) 부분일치. 보관장소 역검색 가능, 띄어쓴 복합 키워드는 문구 전체로 찾아 결과 없음
- **구매단가가 숨는 조건은 권한 설정이 아니라 소속** — `isViewOnly` 가 `dept === "공사팀" || dept.startsWith("보수")` 를 포함
- **유해요인조사표 등록에는 참가자·서명 기능이 없다** — 정식 위험성평가는 위험성평가 등록 메뉴를 써야 함. 또 제출 직후 유/무 표시가 초기화됨(`setPresent({})`)

### 9-5. 그 외

- 기존 매뉴얼 **「작업자용 TBM 등록 및 서명 설명서」(id 2)** 가 작업 중간에 DB에서 사라진 것을 발견해 보고. 두 마이그레이션의 `DELETE` 는 각각 새 제목만 지우므로 이번 작업과 무관 — 사용자가 화면에서 삭제한 것으로 판단(내용이 구 UI 기준이라 신규 2종으로 대체됨). 복구 필요 시 `migration-add-manuals.sql` 에 원문 있음
- `tbm_register.png` 등 기존 매뉴얼 이미지는 **실제 화면이 아닌 컨셉 일러스트**이고 버튼 명칭도 현재 UI와 달라(공사(Repair) 등) 신규 매뉴얼에는 넣지 않고 텍스트 화면 구성도로 대체

## 검증 방식 (이번 세션 공통)

- `npx tsc --noEmit -p .` — 매 변경마다 통과 확인
- **ESLint 회귀 비교** — 변경 전후 지적 건수·항목을 파일 단위로 diff 해 **신규 0건**임을 확인(기존 35건은 전부 `react-hooks/set-state-in-effect` 레거시 패턴). 모바일 인쇄 작업 중 `catch (e: any)` 로 1건 늘어난 것을 발견해 `e instanceof Error` 로 교체
- 참가자 흐름은 **실DB 스모크 테스트**(더미 생성 → 검증 → 삭제, 잔여물 0건 확인)
- 매뉴얼은 **적용 후 `SELECT` 로 제목·정렬순서·본문 길이 확인**(한글 인코딩 포함), 일회성 적용 스크립트 삭제 후 `git status` 로 잔여 없음 확인
