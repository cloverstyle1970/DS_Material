## 1. 초기 설계 판단

### 1-1. 첨부 엑셀 분석

xlsx 파일 파싱 결과: 셀 병합·인쇄 문구는 있으나 **저장된 수식(`f` 필드)이 없음**. 노란색 입력 셀만 남겨진 인쇄용 양식.

즉 사용자가 "엑셀 수식을 적용해달라"고 했을 때 실제로 옮길 계산식은 없었고, 사용자에게 확인해 **산업안전보건공단 2023 여름철 체감온도 공식**(`Tw`/`PT` 2단계 공식)을 채택.

### 1-2. DB 스키마 최초 설계

사용자에게 4가지 확인 후 결정:
1. 저장 위치 → **신규 테이블 세트 5개** (본체 + 부속 4)
2. 서명 정책 → 최초엔 "작업자1 + 관리주체 확인자 서명 필수" (뒤에 몇 번 바뀜)
3. 메뉴명 → **작업일지** (📓)
4. 배치 → **산업안전** 카테고리 안, `/safety/work-journal`

`work_journals` + `work_journal_items` + `work_journal_heat_rests` + `work_journal_participants` + `work_journal_photos` 로 신설.

### 1-3. 사원 참조는 accounts

메모리 [[project-newdb-accounts-schema]] 참고. 마이그레이션 SQL에 `REFERENCES accounts(id)` 로 통일. `users` 는 auth 시스템 테이블이라 비즈니스 코드에서 사용 금지.

## 2. 실시간 기상정보 (Open-Meteo + BigDataCloud)

`fetchCurrentWeather()`가 Geolocation → 병렬로 두 API 호출:

| API | 용도 | 선택 이유 |
|---|---|---|
| **Open-Meteo** `/v1/forecast` | 온도·습도·날씨코드 | API 키 불필요, CORS 지원, 한국 관측소 통합, 상용 무료 |
| **BigDataCloud** `/data/reverse-geocode-client` | 지역명 (한국어) | API 키 불필요, CORS 지원, `localityLanguage=ko` 완벽 지원 |

**판단 근거 — 왜 기상청 API가 아닌가?**
- 기상청 API는 격자 좌표 변환 필요, 인증 키 발급·백엔드 프록시 필요 → 브라우저 직접 호출 불가
- 온도·습도만 필요하고 정확도 준수하면 되므로 Open-Meteo로 충분

**WMO 코드 → 한글 라벨 28종** 매핑을 `weather.ts`에 포함 (0=맑음, 3=흐림, 61~65=비, 71~75=눈, 95=뇌우 등).

지역명 실패해도 `""` 반환하도록 처리 → 지역 조회 실패가 기상 조회 실패로 이어지지 않음.

## 3. 체감온도 4단계 색상 반영 이력

산업안전보건공단 「고온 작업 근로자 온열질환 예방 가이드」 기준:
- 🟢 적정 <31℃ / 🟡 주의 31~33 / 🟠 경고 33~35 / 🔴 위험 ≥35

`heatStressLevel(pt)` 이 `HeatStressInfo { level, label, advice, colorClass }` 반환. `colorClass`는 라이트/다크 모드 모두 포함한 정적 문자열이라 Tailwind가 스캔 가능.

**5곳에 순차 적용:**
1. 상단 환경 지표 체감온도 input
2. 온열질환 안내 카드 (전체 폭)
3. 온열질환 예방 휴게 표(뒤에 삭제됨)
4. 저장된 기상정보 로그 표
5. MyList 상세의 기상정보/휴게 실시 목록

체감온도 표시는 최종적으로 **한 줄 "온도 (단계)"** 형태로 통일 (input과 라벨을 flex row로).

## 4. 연장근무 자동 계산 — 규칙이 3번 바뀜

사용자 요구가 세 번 정정됨:

| 시점 | 규칙 | 결과 |
|---|---|---|
| 1차 | "4시간마다 30분 휴게" | `floor(총분/240) * 30` |
| 2차 | "4h 초과 30분, 8h 초과 60분" | 계단식 |
| 3차 (최종) | "4시간 근무 후 30분 휴게 사이클" | 270분 사이클 반복 |

**최종 로직** (`src/lib/work-hours.ts`):
```ts
const cycles = Math.floor(totalMin / 270);        // 4h 근무 + 30m 휴게
const remainder = totalMin - cycles * 270;
const partialBreak = Math.min(30, Math.max(0, remainder - 240));
const breaks = cycles * 30 + partialBreak;
```

**사용자 스펙 완전 일치 검증**:
- 4시간 1분 → 1분만 차감 (241-1=240) ✓
- 9시간 → 60분 차감 (540-60=480) ✓

## 5. 시간 입력 방식 통일 — `TimeText` 컴포넌트

**초기**: `<input type="time">` 사용. 브라우저별 스피너·AM/PM 표시 문제로 사용자가 반복 문의.

**중간 시도**: `globals.css`에 `::-webkit-datetime-edit-ampm-field { display: none !important; }` 를 넣어 Chromium AM/PM 부분만 숨김.

**최종**: 재사용 컴포넌트 `TimeText`를 만들어 `<input type="text">` 로 전환.
- 숫자만 두들기면 4자리에서 자동 `:` 삽입 (`0930` → `09:30`)
- blur 시 `HH:MM` 정규화 (0~23 : 0~59, zero-pad)
- `inputMode="numeric"` 모바일 숫자 키패드
- placeholder `HH:MM`

**교체 위치 5곳**: 기본근무 시작·종료, 연장근무 시작·종료, 온열질환 휴게 시작·종료, 기상정보 로그 관측시각, 작업 내역 작업 시작·종료.

**중요 판단**: 사용자가 세 번 이상 반복해서 "직접 입력"을 요청. 두 번은 이미 반영되어 있는데도 화면에 안 보인다고 재요청 → 개발서버 로그에서 **참가자 섹션 편집모드 조건부 렌더의 syntax error** 발견. 오류 해소 후에도 사용자 화면 캐시가 오래된 상태였을 가능성. 하드 리로드 안내.

## 6. 참가자 정책 — 요구가 3번 바뀜

| 시점 | 정책 |
|---|---|
| 1차 | 작업자1 자동 채움, 작업자2 필수, 관리주체 확인자 별도 |
| 2차 | 자격/직급 삭제, 최소 2인, +작업자 추가 확장 |
| 3차 | 관리주체 확인자 삭제 (worker만) |
| 4차 | 서명 없어도 저장 가능 + 미서명자에게 알림 |
| 5차 | UI 문구 "선택" → "필수", 빨간색 강조 (정책은 유지) |

**DB 스키마 진화**:
- 초기: `role IN ('worker1','worker2','manager')`
- 2차: `role = 'manager' OR role ~ '^worker[0-9]+$'` (임의 인원)
- 최종: `role ~ '^worker[0-9]+$'` (manager 제거)

`work_journals`의 `worker1/worker2/manager_signature_url` 3개 컬럼은 참가자 확장성을 위해 삭제하고 `work_journal_participants.signature_url` 로 통합.

**서명 정책의 핵심 판단**: 검증에서 서명을 필수로 두면 미서명자가 있을 때 저장 자체가 불가. 사용자는 "저장 가능 + 알림 발송" 을 원함. UI 라벨은 "필수 — 없으면 알림 발송" 으로 사용자에게 강한 압박, 실제 저장 로직은 관대. 미서명 방치를 방지하기 위해 미서명자 자기 서명 추가 UI(모달)를 별도 제공.

## 7. 미서명자 서명 추가 모달 확장

초기엔 SignaturePad + 저장 버튼만. 사용자가 "서명 시 내용 확인 가능하게" 요청 → 저널 본체 + 부속 3개(items/rests/env_readings) 조회 후 요약 카드 표시로 확장.

표시 순서: 기본 정보 → 작업구분 → 환경 지표 → 근무 시간 → 작업 내역 표 → 온열질환 예방 휴게 실시 → 기상정보 로그 → 특이사항 → 서명 패드.

체감온도는 `heatStressLevel()` 로 색상 배지. 표는 `<table>` 로 정돈. 서명 저장 → `work_journal_participants.signature_url` UPDATE → `onSaved` → MyList 상세 재로딩.

## 8. 저장 후 수정 기능

**진입점**: MyList 상세 카드의 ✏️ 수정 버튼 → `WorkJournalClient.editingId` 세팅 → 서브탭 "write"로 전환 → `WorkJournalWriteForm`에 `editingJournalId` prop 전달.

**로드**: 저널 + 부속 3개 병렬 조회 → state 채움. `TIME` 컬럼은 `.slice(0, 5)` 로 `HH:MM` 정규화.

**저장 분기 (핵심 판단)**:
```ts
if (editingJournalId) {
  // UPDATE work_journals + updated_at 갱신
  // 부속 3개 delete → insert 방식 (전체 교체)
  // 참가자 미변경, 서명 업로드 스킵, 미서명자 알림 스킵
} else {
  // INSERT 기존 흐름
}
```

**참가자를 편집 대상에서 제외한 이유**: 서명은 최초 시점의 진정성이 산업안전 서류로서 중요. 참가자 편집을 허용하면 저장 후 임의 변경 우려. 대신 미서명자 자기 서명 추가 UI로 보완 경로 제공.

**UI 힌트**:
- 편집 시 참가자 섹션 자리에 안내 문구 카드 렌더 (편집 불가 명시)
- 서브탭 라벨 "✍️ 작성" → "✏️ 수정"
- 저장 버튼 "📤 작업일지 저장" → "💾 수정 저장"
- 우측에 "수정 취소" 링크

## 11. 세션의 특징 — 지속 정정 반영

이번 세션은 **한 번의 큰 설계 결정 후 20여 회의 세부 정정** 형태. 사용자가 실제 UI를 보며 반복 개선 요청:
- 컬럼 순서 변경 (실시 → 맨 앞)
- 컬럼 삭제·추가 (실시/온도/습도/체감온도 → 휴게방법)
- 라벨 정리 (호기별 삭제, 빨간색 강조)
- 시간 입력 방식 (time picker → TimeText 텍스트)
- 규칙 정정 (연장 휴게 계산 3회, 서명 정책 5회)

**대응 원칙**:
- 데이터가 0건인 초기 단계라 파괴적 스키마 변경도 즉시 반영
- 마이그레이션 파일은 idempotent (`IF EXISTS/NOT EXISTS`, `DROP POLICY IF EXISTS` 등)
- 원본 마이그레이션 SQL을 매번 최종 상태와 정합
- 사용자가 캐시 문제로 반영 안 됨을 착각하는 경우 → 개발서버 로그 확인 후 하드 리로드 안내

## 12. 검증 방식

각 변경 후:
1. `npx tsc --noEmit -p .` — 타입 오류 없음
2. `curl` 로 `GET /safety/work-journal` 200 응답 확인

4. DB 변경은 검증 SELECT로 컬럼 존재 재확인

**개발서버 syntax error 1회 발생**: 참가자 섹션 조건부 렌더 `{editingJournalId ? (...) : (...)}` 를 SWC 파서가 오해석해 컴파일 실패. tsc는 통과했으나 Next dev 로그에서 발견. 편집 이후 서버가 정상 응답으로 회복.
