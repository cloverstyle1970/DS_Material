## 2. SSO `session_not_found` 디버깅

유지보수 측에서 met 진입 시 `/auth/v1/user` 403 `session_not_found` 가 계속 발생한다는 보고. 그쪽 분석은 "양측 코드 OK인데 토큰 거부됨" 결론이었으나, 우리 측 코드를 재검토하면서 명확한 진원지 발견:

`src/context/AuthContext.tsx`의 `syncFromSession()` 두 분기:

```ts
// 127-132: session.user.email 의 id 파싱 실패 분기
if (!Number.isFinite(id) || id <= 0) {
  await supabase.auth.signOut();
  ...
}

// 170-175: accounts 행이 없는 분기
} else {
  await supabase.auth.signOut();
  ...
}
```

`signOut()` 은 `/auth/v1/logout` 호출로 **서버 측 sessions row delete + refresh_token revoke**. men ↔ met 가 같은 Supabase 프로젝트의 같은 `auth.sessions` row를 공유하므로, 한쪽에서 호출하면 다른 쪽도 즉시 `session_not_found` 가 된다.

가장 유력한 시나리오:
1. men 측이 hash로 토큰 송신 (정상)
2. met `consumeSsoHashIfPresent` → `setSession` 성공 (sessions 살아 있음)
3. met `syncFromSession` 이 `session.user.email` 파싱 → 우리 규약(`${accounts.id}@daesol.el`) 불일치 또는 `accounts` 행 부재
4. 우리가 `signOut()` 호출 → 서버 sessions row 삭제
5. 그 뒤 SDK 후속 `/auth/v1/user` 호출 → 403 `session_not_found`
6. user=null → `AdminShell.tsx:31-35` → `/login` 리다이렉트

### 패치 (커밋 `28f1e4d`)

`AuthContext.tsx`:
- `consumeSsoHashIfPresent()` 가 `Promise<boolean>` 반환 (setSession 성공 여부)
- `syncFromSession({ skipSignOut?: boolean })` 옵션 추가, SSO 진입 경로에서는 두 signOut 분기 우회
- IIFE: `cameViaSso` 를 받아 `syncFromSession({ skipSignOut: cameViaSso })`

이제 met 가 SSO 토큰을 받고 email 규약 불일치/계정 부재 분기에 빠지더라도 서버 sessions를 지우지 않으므로 men 측 동일 세션 보존. session_not_found 연쇄 차단.

유지보수 측에 회신: men 측의 "송신 직전 `await db.auth.refreshSession()` 추가"가 오히려 race(autoRefreshToken 백그라운드 refresh로 송신 토큰 폐기)를 만들 수 있어 제거 후 재시도 권장.
